# How locators compose

Generated from `analysis/composition-patterns.mjs` and `e2e/patterns/s14-composition.spec.ts`.
Run `npm run composition-doc` after changing either. Do not edit this file.

Every other document here measures one locator against one element. Nobody writes
tests that way. A real suite hands a locator out of a fixture, chains onto it,
stores it on a page object and indexes into it - and most of the ways a suite goes
wrong live in that composition rather than in the choice of engine.

Each pattern below is a DO/DON'T pair that answers the same question both ways, and
each one is proved by a scenario rather than asserted here:

- **cost** - both forms work, and the DON'T is measurably slower. Paired
  measurement, baseline subtracted, median of the repetitions, same as every other
  timing in this project.
- **outcome** - the DON'T is simply wrong. The proof is what it produced.

Proofs below come from run `20260921090556` on Chromium 141.0.7390.37: 13 of 13 patterns.

```bash
npm run bench:patterns   # writes results/composition.json
npm run composition-doc  # rewrites this file
```

## What the examples are written against

The examples share one scenario file, so they share its fixture and page object.
`grid` below is that fixture. The page object hands out locators rather than
elements, which is itself the first pattern.

```ts
/** Production-ish page: ~30,000 elements, matching S1's `m` tier. */
const BIG = { rows: 1_500, cols: 6, seed: 'bm-v1' } as const;
const BIG_ROW = 750;
const BIG_COL = 2;
/** Column 2's accessible name on that row, stamped by the target directive. */
const BIG_NAME = `Status for row ${BIG_ROW}`;

class GridPage {
  constructor(private readonly page: Page) {}

  /** A uniquely addressable container. Everything else is scoped through it. */
  row(r: number): Locator {
    return this.page.getByTestId(`row.${r}`);
  }

  /** Deliberately takes a root: the caller decides what this is scoped to. */
  cellByName(root: Locator, name: string): Locator {
    return root.getByRole('button', { name, exact: true });
  }
}

/**
 * A fixture that hands the test a page object rather than a resolved element.
 *
 * The fixture never awaits anything about the DOM, so it cannot bake in a state
 * that has already changed by the time the test body runs.
 */
const test = base.extend<{ grid: GridPage }>({
  grid: async ({ page }, use) => {
    await use(new GridPage(page));
  },
});
```

## Fixtures and page objects

A locator is a description of how to find something, not something found. Almost every
fixture mistake is a variation on forgetting that: resolving too early, storing the
result, or storing it somewhere that outlives the page it came from.

### Hand out locators, not element handles

A fixture that resolves the element hands the test a pointer to a node that may no
longer exist.

```ts
// DON'T
// A fixture that resolves the element and hands back the handle.
const handle = await page.getByTestId('churn.12').elementHandle();

// DO
// A fixture that hands back the locator instead.
const target = page.getByTestId('churn.12');
```

An ElementHandle points at one specific DOM node. A locator points at a query. When the
framework re-renders - a signal updates, a list re-keys, a route reloads - the node the
handle holds is detached, and every action on it fails against a DOM nobody is looking
at any more. The locator runs its query again and finds the element that exists now.
This is also why a fixture can safely build locators before the test does anything at
all.

**Proved:** element handle detached after one re-render; click failed with
"elementHandle.click: Element is not attached to the DOM". Instead, locator re-resolved
and clicked the current element. Measured on a list that replaces its nodes on every
tick.

`/churn?rows=40&hz=10&trackby=0`

### Do not await DOM state in a constructor

A page object that counts, reads text or checks visibility while being built captures a
moment that has already passed.

```ts
// DON'T
// A page object that resolves state while it is being constructed.
const submitCount = await page.getByTestId('late.slot').getByRole('button').count();

// DO
// A page object that exposes the locator and lets the assertion do the waiting.
const submit = page.getByTestId('late.slot').getByRole('button', { name: 'Submit' });
await expect(submit).toHaveCount(1);
```

Fixtures run before the test body, which is usually before the application has settled.
A count taken there is not wrong later - it was wrong when it was taken. Expose the
locator and let the assertion do the waiting; the page object stays cheap to construct
and correct at every point in the test.

**Proved:** count() in the constructor returned 0. Instead, the same locator, asserted
rather than counted, resolved to 1. The control arrives 800 ms after the app reports its
first render.

`/late?lateMode=append&delay=800&rows=200`

### Build locators before the page exists

Locators can be constructed against a blank page, in a fixture, at module scope - they
resolve when used.

```ts
// DON'T
// The same intent, resolved eagerly: there is nothing to find yet.
const handleBefore = await page.$('button');

// DO
// Built against a blank page: a locator is a description, not a lookup.
const submit = page.getByRole('button', { name: 'Submit' });
```

This is the property that makes page objects work. Because nothing is resolved until an
action or an assertion runs, a page object can be constructed once and used across
navigations without rebuilding anything. The eager equivalent cannot exist yet, and has
to be re-resolved after every navigation - which is the bug in every "element not
attached" stack trace.

**Proved:** page.$() before navigation returned null, and would have to be re-resolved
after every navigation. Instead, the locator built before navigation resolved to 1
element afterwards. Both forms attempted before navigation, then used after it.

`/late?lateMode=append&delay=0&rows=200`

### A locator belongs to one page

Locators carry their frame. One captured from the first page keeps querying the first
page.

```ts
// DON'T
// A locator captured from one page, then used after opening another.
const rowsOnFirstPage = page.locator('tr.bm-grid__row');
const second = await context.newPage();
await second.goto('/grid?rows=40&cols=6&seed=bm-v1', { waitUntil: 'commit' });
await second.waitForSelector('html[data-bm-ready]');
const seenFromFirst = await rowsOnFirstPage.count();

// DO
// Each page gets its own locators, built from that page.
const rowsOnSecondPage = second.locator('tr.bm-grid__row');
const seenFromSecond = await rowsOnSecondPage.count();
```

A locator is bound to the frame that created it, so passing one between fixtures,
storing one at module scope, or keeping one across a popup or a new tab silently queries
the wrong document. There is no error - the query runs, against the page you were not
looking at. Build locators from the page object you were handed, and give a second page
its own.

**Proved:** the captured locator kept reporting 5 rows, its own page's count, after a
second page opened. Instead, a locator built from the second page reported 40. Two pages
open at once, with different row counts, in the same context.

`/grid?rows=5&cols=6&seed=bm-v1`

## Scoping and chaining

Chaining is not the problem. Chaining from a root that matches thousands of elements is,
because every step re-resolves against every match of the step before it. Give the first
step one match and the multiplication disappears.

### Scope the expensive query, keep the assertion

Find the container by identity; find the control inside it by role and name.

```ts
// DON'T
// Every element of that role in the document is a candidate.
const unscoped = page.getByRole('button', { name: BIG_NAME, exact: true });

// DO
// The container is found by test id; the accessible name is asserted inside it.
const scoped = grid.cellByName(grid.row(BIG_ROW), BIG_NAME);
```

An unscoped role query computes an accessible name for every element of that role in the
document. Scoped to a container it computes one per candidate inside that container. The
test still asserts that the control is reachable by its accessible name - which is the
thing worth asserting - and stops paying for the rest of the page to be examined.

**Measured** (30,034 elements): 208.2 ms to **38.3 ms**, 5.4 times faster. Same element,
same accessible name, one paired measurement each.

`/grid?rows=1500&cols=6&seed=bm-v1`

### Chain from something unique

The cost of a chain is the product of the match counts along it.

```ts
// DON'T
// Each step re-resolves against every match of the step before it.
const fromBroadRoot = page
  .locator('tr.bm-grid__row')
  .locator('td.bm-grid__cellwrap')
  .locator('button.bm-grid__cell')
  .nth(index);

// DO
// Identical chaining, but the first step matches exactly one element.
const fromUniqueRoot = grid.row(BIG_ROW)
  .locator('td.bm-grid__cellwrap')
  .locator('button.bm-grid__cell')
  .nth(BIG_COL);
```

Each chained step runs its selector against every element the previous step matched.
Three broad steps over a large table is thousands of subqueries; the same three steps
from a container that matches exactly one element is three. The fix is never "stop
chaining" - it is to make the first step unique.

**Measured** (30,034 elements): 2.01 s to **35.4 ms**, 56.6 times faster. Identical
chains, differing only in whether the first step matches one element or every row.

`/grid?rows=1500&cols=6&seed=bm-v1`

### Filter a narrow set, or address the element instead

filter({ hasText }) runs a text scan per candidate, so the cost follows the candidate
count.

```ts
// DON'T
// Every row is a candidate, and each candidate pays a text scan.
const filtered = page
  .getByRole('row')
  .filter({ hasText: `Row ${BIG_ROW} ` })
  .getByRole('button', { name: BIG_NAME, exact: true });

// DO
// The row is addressed directly; there is nothing left to filter.
const addressed = grid.cellByName(grid.row(BIG_ROW), BIG_NAME);
```

Filtering is the right tool when the thing you want can only be described by its
content, and the candidate set is already small. Reaching for it against every row of a
table means scanning the text of every row to find the one whose identity you already
knew. If the container has a test id, use it.

**Measured** (30,034 elements): 178.2 ms to **9.1 ms**, 19.6 times faster. Filtering
every row against addressing the row directly.

`/grid?rows=1500&cols=6&seed=bm-v1`

## Strict mode and ambiguity

Strict mode fails a test when a locator matches more than one element. That failure is
the feature. Both ways of silencing it - taking the first match, or indexing into the
list - replace a loud failure with a test that passes against the wrong element.

### Never silence a strict-mode violation with .first()

.first() takes whatever is first in document order, which is rarely the element you
meant.

```ts
// DON'T
// The strict-mode violation is real; .first() hides it and takes whatever is
// first in document order.
const first = page.locator(`#${canonicalId}`).first();
const clash = await first.getAttribute('data-clash');

// DO
// Scope to something that is genuinely unique, and let strict mode stand.
const scoped = page.getByTestId('card.30').getByRole('button', { name: 'Open 30', exact: true });
const testId = await scoped.getAttribute('data-testid');
```

A strict-mode violation says the locator does not identify one element. .first() does
not fix that; it picks one and carries on, and the test passes against whatever happens
to render earliest. When something is later inserted above your target - a banner, a
duplicate id, a second instance of the component - the test keeps passing and stops
testing what it claims to. Narrow the root instead.

**Proved:** .first() resolved to a decoy (data-clash="0") while reporting success.
Instead, the scoped locator resolved to data-testid="action.30". Four elements
deliberately reuse the target id, rendered ahead of it.

`/ambiguous?dup=60&dupIds=4&target=30`

### nth() indexes the template, not the data

Position is owned by whoever edits the markup, which is not whoever wrote the test.

```ts
// DON'T
// Position within the row, which the template owns.
const byPosition = grid.row(10).getByRole('button').nth(BIG_COL);

// DO
// Identity within the row, which the data owns.
const byIdentity = grid.row(10).getByTestId(`cell.10.${BIG_COL}`);
```

Indexing into a list of matches ties the test to DOM order. Reordering columns, adding a
button, or rendering an extra element conditionally changes what the index refers to,
and nothing fails - the test asserts confidently against a different element. Where a
stable identity exists, address it; nth() is defensible only in a tree you fully
control, such as a component test.

**Proved:** nth(2) resolved to column 2 before the reorder and column 3 after it.
Instead, the identity locator resolved to column 2 both times. The same two locators
before and after the column order is reversed.

`/grid?rows=40&cols=6&seed=bm-v1&mutate=reorder`

## Waiting and assertions

Anything you await into a variable is a snapshot with no retry. Anything you pass to
expect() is re-read until it agrees or the timeout expires. Most flaky tests are a
snapshot being asserted against a page that had not finished moving.

### count() asks, toHaveCount() waits

Locator queries return what is true right now. Web-first assertions retry until the
timeout.

```ts
// DON'T
// A snapshot of right now. No retry, so the assertion runs against whatever
// the page happened to be mid-render.
const countNow = await submit.count();

// DO
// Retries until the page agrees or the timeout expires.
await expect(submit).toHaveCount(1);
```

await locator.count() resolves immediately against a page that may still be rendering,
and the number it returns is then asserted with no retry. expect(locator).toHaveCount(n)
re-runs the query until it matches or gives up. The difference is the difference between
a flaky suite and a slow one, and only one of those is worth having.

**Proved:** count() returned 0 while the control was still 800ms away. Instead,
toHaveCount(1) retried for 798ms and passed. The control appears 800 ms after the page
reports itself rendered.

`/late?lateMode=append&delay=800&rows=200`

### all() freezes a list that has not stopped moving

It returns positional locators captured at one moment, and positions change.

```ts
// DON'T
// A frozen array of positional locators. Each one means "the nth match as of
// whenever you next use it", which is not the element you looked at.
const items = await page.getByTestId('churn.list').locator('.bm-churn__cell').all();
const thirdValueThen = await items[3].textContent();

// DO
// Address the item, not its position, and assert on the locator.
const item = page.getByTestId('churn.3');
await expect(item).toHaveAttribute('data-row', '3');
```

locator.all() resolves the matches once and hands back an array of nth-indexed locators.
If the list re-renders, re-sorts or grows, entry 3 still means "the fourth match
whenever you next use it" - which may now be a different item. Assert the count first if
you must iterate, and address items by identity inside the loop rather than by where
they were.

**Proved:** items[3] read "v3.1" and then "v3.2" without anything re-reading the list.
Instead, an identity locator kept pointing at data-row="3" across the same re-render. A
list that re-keys every tick, read twice through the same array.

`/churn?rows=40&hz=10&trackby=0`

### An awaited value is not an assertion

textContent(), inputValue() and getAttribute() return strings, and strings do not retry.

```ts
// DON'T
// A string. Whatever it says, it says forever.
const text = await cell.textContent();

// DO
// The locator, asserted. Re-reads the element until it agrees or times out.
await expect(cell).toHaveText(textNow ?? '');
```

Capturing a value and asserting on the variable moves the assertion off the page and
into your process. Whatever the string said when it was read, it says forever - so a
test can pass against a value the interface stopped showing seconds ago, or fail because
the read landed one frame early. Pass the locator to expect() and let it re-read.

**Proved:** the captured string still reads "v7.0" after the element changed to "v7.1".
Instead, the assertion re-read the element and matched its current value. Both reads
taken across one re-render of the same element.

`/churn?rows=40&hz=10&trackby=0`

### A fixed sleep pays the worst case every time

waitForTimeout costs the same on a fast machine and is still too short on a slow one.

```ts
// DON'T
// Costs the same whether the page took 10ms or 2 seconds, and still fails when
// the machine is slower than whoever picked the number.
await page.waitForTimeout(sleepMs);
await expect(submit).toHaveCount(1);

// DO
// Returns as soon as the page is ready, and waits longer when it has to.
await expect(page.getByTestId('late.slot').getByRole('button', { name: 'Submit' })).toHaveCount(1);
```

A sleep encodes a guess about someone else's hardware. It is pure cost when the page was
ready immediately, and it fails anyway when CI is loaded. A web-first assertion returns
as soon as the condition holds and waits longer when it has to - faster in the common
case and more reliable in the bad one. There is no trade-off here to weigh.

**Measured** (223 elements): 3.02 s to **802.0 ms**, 3.8 times faster. Wall clock for
each form, against a control that appears after 800 ms.

`/late?lateMode=append&delay=800&rows=200`

## What this does not claim

- The cost figures are one machine, one browser build, one page shape. The ratios
  are the point, not the absolute milliseconds.
- Nothing here says chaining, filtering or `nth()` are wrong. They are wrong in the
  situations shown, for the reasons shown, and each pattern says what to do instead.
- A pattern proved by outcome is proved for the case the scenario builds. That a
  detached handle fails is a property of the API; that your suite has one is not
  something this can tell you.
