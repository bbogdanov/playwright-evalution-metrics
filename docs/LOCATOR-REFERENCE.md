# Locator reference

What every strategy in the benchmark matrix actually executes, and what it cost.

Generated by `npm run reference`. The calls are produced by running each
strategy's own `build()` function against a recording stand-in for the Page, so
they are the real call chains rather than a transcription — if the
implementation changes, this file changes with it.

The example target is a grid cell at row 750, column 2, as the benchmark app
renders it:

```html
<button id="cell-r750-c2" data-testid="cell.750.2" data-qa="ebc69256"
        class="bm-grid__cell bm-cell bm-cell--v2 _a854d9"
        aria-label="Status for row 750" title="Status for row 750"
        data-kind="cell" data-row="750" data-col="2">status-750-2-ft8o</button>
```

## Measurement context

- **Machine**: Intel(R) Xeon(R) Processor @ 2.80GHz ×4, load 0.39
- **Toolchain**: Playwright 1.63.0, Chromium 141.0.7390.37, Node v22.23.2
- **Page**: largest tier measured (`l`), ~120,000 DOM elements, target at depth 9
- **Noise floor**: 0.049 ms — differences smaller than this are not differences
- **For scale**: a click on a quiet page costs 49.94 ms
- **Caveat**: Chromium build 1194 in use; this Playwright ships 1243. Results are valid for the pair exercised, not for the default pairing.

Costs are medians, net of a paired baseline. They are valid for this machine
only — a faster machine moves every number, and the ratios matter more than the
absolutes.

## What each one is for

| Strategy | What it asks the browser to do |
|---|---|
| `testid.api` | getByTestId with the configured testIdAttribute |
| `testid.css` | The same attribute written as a raw CSS attribute selector |
| `testid.engine` | page.locator with the data-testid selector engine, no helper wrapper |
| `id.engine` | page.locator with the id selector engine rather than a CSS # selector |
| `id.css` | CSS id selector; the theoretical best case for any engine |
| `qa.attr` | Opaque generated unique attribute: maximally stable, unreadable |
| `attr.compound` | Three data attributes combined; unique without a dedicated test id |
| `title.api` | getByTitle: attribute match, but ambiguity depends on copy |
| `class.semantic` | Bare semantic class; ambiguous the moment the list has two rows |
| `class.semantic.nth` | Semantic class disambiguated by index: unique, and order-dependent |
| `class.compound` | Semantic plus variant class; narrower, still not unique |
| `class.hashed` | Build-hashed class, as emitted by CSS modules or scoped styles |
| `css.chain.full` | Full ancestor chain from <body>, i.e. devtools "Copy selector" |
| `xpath.absolute` | Positional absolute XPath, the most brittle form available |
| `xpath.relative` | Attribute-predicated XPath; no ancestry, but still no shadow piercing |
| `role.name` | getByRole with an accessible name; no native equivalent exists |
| `role.locator` | The same role query written for page.locator: role=button[name="X"s] |
| `role.bare.nth` | getByRole without a name, disambiguated by index |
| `text.exact` | getByText, exact match on normalised visible text |
| `text.locator` | The same text query written for page.locator: text="X" (quoted means exact) |
| `text.substring` | getByText substring match; scans and compares every text node |
| `filter.hasText` | Class locator narrowed by hasText: a text scan per candidate |
| `filter.has` | Find the container holding X, then the leaf inside it: a subquery per candidate |
| `css.has` | CSS :has() evaluated as a subquery per candidate container |
| `css.hasText` | The :has-text() pseudo-class: a text scan per candidate |
| `css.visible` | The :visible pseudo-class; forces layout for every candidate |
| `scoped.role` | Container test id, then role inside it: the standard advice |
| `scoped.class` | Container test id, then semantic class inside it |
| `chained.locator` | Chained .locator() calls rather than one compound selector |
| `nth.engine` | Positional selection through the nth= engine rather than the .nth() helper |
| `mixed.engine` | CSS handed to a text engine via >>; two engines, one locator |

## What the work actually is

Timings tell you which locators are slow. These numbers come from a Chrome
trace and tell you *why*, by counting the timeline events a query produces
rather than measuring how long it runs. Counts are a property of the engine, so
they hold on any machine and at any page size — which is why this is measured on
a small tier and never fed into the timing analysis.

| Strategy | Candidates | Forced layouts / query | Per candidate |
|---|---|---|---|
| `css.visible` | 1200 | 1200 | **1.00** |

Every other strategy in the matrix forces zero. So `:visible` is not "somewhat
more expensive" — it reads layout once for every element it considers, and that
is counted here, not inferred from the shape of a timing curve.

Garbage-collection time was also recorded, to test whether the role and text
engines show allocation pressure from building strings per candidate. **It does
not separate them.** The heaviest reading is `chained.locator` at
2.57 ms/query, but `id.engine` — an id lookup that
touches one element — reads 0.00 ms/query, which is the same
band. GC is not attributed to whatever caused the allocation, so these numbers
carry no signal about which locator did the work. Recorded and reported as a
dead end rather than dressed up as support.

## Reading the numbers

**"At floor" is not "free".** It means the query costs less than the round-trip
jitter it is measured against, so the honest statement is "indistinguishable from
the cheapest thing we can measure" rather than a number.

**Chaining is not the same as a compound selector.** `chained.locator` and
`css.chain.full` reach the same element by the same three steps, and one is
thousands of times slower: each chained `.locator()` re-resolves against every
match of the step before it, so the work is a product of the counts rather than a
single pass. This is the largest avoidable difference in the whole matrix.

**The `filter` family multiplies.** `filter({ has })` and `:has()` run a subquery
per candidate container, and `:visible` forces a layout read per candidate.
Cheap on a small list, pathological on a large one.

**The role family has no native floor** because no DOM API computes accessible
names, so there is nothing to compare Playwright against. The traced profile
confirms it forces no layout, so whatever it spends goes on script — but the
trace does not say what, and the GC figures do not separate it from a bare id
lookup. That role queries compute a name per candidate is the documented
behaviour of the API and fits the timings; it is **not** something this
benchmark has measured directly.

**Speed is the least important column here.** A locator that is unique and
survives refactoring, but takes a few milliseconds, costs nothing anyone will
notice. A locator that silently matches the wrong element costs an afternoon. The
ranking in the dashboard weights it accordingly.
